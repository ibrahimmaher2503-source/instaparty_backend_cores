# Implementation Plan: Booking — Draft Creation & Item Management

**Branch**: `005-booking-draft-items` | **Date**: 2026-04-30 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/005-booking-draft-items/spec.md`

---

## Summary

Allow authenticated customers to create draft bookings, add items from multiple vendors with per-type inventory reservation (15-minute TTL), and remove items with automatic reservation release. Each product type (rental, sale, digital) runs a distinct fulfillment state machine on `booking_items.item_status`. Pessimistic locking via `booking_locks` prevents overselling. Per-vendor subtotals are computed in real time.

Depends on: Catalog module (Phase 2.0) — `services` and detail tables must exist. Identity module (Phase 1.0) — authenticated customer sessions.

## Technical Context

**Language/Version**: PHP 8.3, Laravel 12
**Primary Dependencies**: `spatie/laravel-model-states` (per-type state machines), `spatie/laravel-permission`, `brick/money`, `spatie/laravel-translatable`
**Storage**: MySQL 8 / MariaDB 11 — 10 booking tables
**Testing**: Pest — Feature tests in `tests/Feature/Modules/Booking/`
**Target Platform**: Linux (Docker Compose)
**Project Type**: Modular monolith API — `app/Modules/Booking/`
**Performance Goals**: Reservation acquisition under 200ms p95; total computation instant (in-DB aggregation)
**Constraints**: Pessimistic lock required for last-unit oversell prevention; 15-min TTL enforced by scheduled command; three distinct state machines on one `item_status` column; all three product types mandatory
**Scale/Scope**: Phase 3.1 — customer basket creation only; payment and vendor response in Phase 3.2+

## Complexity Tracking

No constitution violations. No unjustified complexity.

| Decision | Why Needed |
|---|---|
| `booking_locks` application-level lock table | `SELECT ... FOR UPDATE` alone is insufficient across worker processes; `booking_locks` provides cross-request lock tokens with TTL |
| Three state hierarchies on one `item_status` column | Spec mandates distinct graphs per type; using a per-type state base class + `match($productType)` for resolution avoids three separate columns while keeping type-safe transitions |
| `ReleaseExpiredReservationsCommand` scheduled job | Reservation TTL cannot rely on DB triggers (not in stack); the job runs every minute via Laravel scheduler |

## Implementation Order (Day by Day)

### Day 1 — Schema, Models, State Machines

1. Write 8 migrations in dependency order (see file list above)
2. Generate Eloquent models with relationships and casts
3. Implement three state machine hierarchies in `Domain/States/`
4. Write `BookingServiceProvider`: load migrations, routes, listeners, bind contracts
5. Write `EloquentBookingRepository` implementing `BookingRepository` contract
6. Write `CatalogServiceReader` contract + implementation (reads `services` table via Catalog's repository or direct query — documented in research.md R5)

### Day 2 — Actions, API, Tests

1. `CreateBookingDraftAction` — creates booking + address + initial snapshot
2. `AddItemToBookingAction` — acquires booking lock → checks inventory → writes reservation → creates booking_vendor (or upserts) → creates booking_item → triggers total recalculation
3. `RemoveItemFromBookingAction` — releases reservation → deletes item → removes booking_vendor if empty → recalculates totals
4. `ReleaseExpiredReservationsCommand` — batch-updates expired `held` reservations
5. HTTP layer: controllers (3-line bodies), requests, resources
6. Pest tests (see test plan in data-model.md)
